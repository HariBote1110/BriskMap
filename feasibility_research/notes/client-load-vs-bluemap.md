# ブラウザ側の負荷: BriskMap と BlueMap の比較

## 目的 / 仮説

BriskMap はサーバーで描画しない分、3D の形の組み立てをブラウザで行う。利用者の端末にかかる負荷が BlueMap と比べてどうなるかを、同じカメラ・同じ表示範囲で比べる。

Dynmap は描画済み画像を並べるだけなので、ブラウザ側の計算負荷は小さいと見込み、今回は対象外とする（通信量・リクエスト数は多い）。

- **H6（転送量）:** 近距離 3D の範囲を揃えた条件（半径 256 ブロック）で、BriskMap の転送量は BlueMap の **1/3 以下**。
  - 根拠: BlueMap は斜め視点（距離 120）で近距離 3D だけで 238 件・11.2 MB を読み込んだ。BriskMap の 3D データ（hide/surface）は 1 リージョン平均約 0.75 MB で、半径 256 ブロック（約 804 チャンク）なら 1 MB 未満の見込み。
  - 棄却条件: 1/3 を超える。
- **H7（CPU 時間）:** 読み込み完了までのブラウザ全体の CPU 時間は、BlueMap の **2 倍以内**（BriskMap は組み立てを行う分、増える前提）。
  - 棄却条件: 2 倍を超える。
- **H8（GPU メモリ）:** GPU に送るデータ量は BlueMap 以下。BlueMap の頂点は UV・法線・色・AO などの属性を持つため、1 頂点 12 バイトの BriskMap のほうが小さいと予想する。
  - 棄却条件: BlueMap を上回る。
- **H9（fps）:** カメラを 10 秒で 1 周させたときの平均 fps は、両者とも 55 以上（Apple M4、1600×900、倍率 1）。

## 比較の条件（公平性）

- 案 A: 近距離 3D の範囲を両者とも半径 256 ブロックに揃え、BlueMap の遠景（lowres）は 0 にする。
- 案 B: BlueMap は既定設定（近距離 100、遠景 2,000）。利用者が実際に受ける負荷の参考値。BriskMap は案 A と同じもので比べない。
- BriskMap は色のみ（テクスチャ・光・影なし）、階段なども立方体。BlueMap はテクスチャ・光・AO あり。**BriskMap に有利な差であることを結論に明記する。**
- BriskMap のデータは `--caves hide --fluids surface`（BlueMap の既定 `remove-caves-below-y: 55`、水面のみの描画に近い）。
- 配信は両方とも検証用コンテナ（192.168.0.175）から LAN 越し。BlueMap は組み込み Web サーバー（ポート 8100、gzip）、BriskMap は Range 対応の静的サーバー（ポート 8200）。

## 環境

- ブラウザ: Mac mini（Apple M4、10 コア、32GB）上の Google Chrome for Testing（Playwright chromium-1223、GPU あり、画面表示あり）。実行ごとに新しいプロファイル、キャッシュ無効、ウィンドウ 1600×900、`--force-device-scale-factor=1`
- 測定: `tools/clientbench/`（CDP で操作）

## 手順

- 配信（検証用コンテナ）:
  - BlueMap: `java -Xmx2G -jar bluemap-5.16-cli.jar -w`（ポート 8100）
  - BriskMap: `node viewer/serve.mjs --root /opt/bench/tools --data /opt/bench/brisk/v2-hide-surface --port 8200 --host 0.0.0.0`（Node 20.19.2、`tools/viewer` と `tools/mesher/{src,dist}` を配置）
- 測定（Mac）: `cd tools/clientbench && node run.mjs --chrome "<Google Chrome for Testing>" --scenarios scenarios.json --runs 3 --out ../../output/clientbench/results.jsonl`
  - 実行ごとに新しい Chromium を起動。BlueMap を先に測り、BlueMap が地形に合わせた注視点の高さ（y）を BriskMap に渡す。
  - 視点: top（距離 400、回転 0、角度 0.1）、oblique（150、0.6、0.9）、low（40、0.6、1.4）。注視点は x=0, z=0。
  - 「落ち着いた」判定: 通信中のリクエストが 0、かつ通信とロングタスク（50ms 超）が 2 秒間なし（BriskMap は加えて `__briskReady`）。
  - CPU 時間は Chromium のプロセスツリー全体を `ps` で測った合計（Worker は renderer に含まれる）。JS ヒープはメインスレッドのみ。
  - GPU への転送量は WebGL の `bufferData` などを横取りして数えた値。
  - 1 周: カメラを注視点の周りに 10 秒で 1 回転。

### 測定道具の不具合と修正（結果に影響したもの）

- ビューアの Worker が、チャンクごとに `mesher.wasm` を読み直していた（同時に届いたメッセージがそれぞれ読み込みを始める競合）。864 回の取得で転送量が 57 MB になっていた。修正後は Worker 1 本につき 1 回（コミット「fix: ビューアの Worker がチャンクごとに WASM を読み直す競合を修正」）。
- ハーネスが Worker のスクリプト取得の「開始」と「完了」を別セッションで受け取り、対応付けられずに 180 秒待ちになっていた。requestId だけで対応付けるよう修正。
- BlueMap のテクスチャ（`data:` URL、2,102 件）がリクエストとして数えられていた。転送量・件数から除外し、別項目に記録。

## 結論（案 A: 近距離 3D の範囲を揃えた比較）

| 項目 | BriskMap / BlueMap |
|---|---|
| 転送量 | **5.7%**（0.86 MB / 14.93 MB） |
| リクエスト数 | 34%（98 / 289） |
| 落ち着くまでの時間 | **約 1/3.7**（約 0.42 秒 / 約 1.56 秒） |
| 読み込み中の CPU 時間 | **33〜43%**（約 2.0 秒 / 4.6〜6.0 秒） |
| GPU バッファ | **14〜30%**（27.8 MB / 92〜204 MB） |
| 1 周中の CPU 時間 | **20〜34%**（約 1.9 秒 / 5.5〜9.4 秒） |

- **H6（転送量 1/3 以下）: 採択。** 5.7%。
- **H7（CPU 時間 2 倍以内）: 採択。** 組み立てをブラウザで行っているにもかかわらず、BlueMap より少ない（33〜43%）。
- **H8（GPU メモリ BlueMap 以下）: 採択。** 14〜30%。
- **H9（両者 fps 55 以上）: 採択。ただし判別力なし。** 両者とも 60Hz の上限に張り付いている（p99 16.9 ms）。描画の重さの差は「1 周中の CPU 時間」に表れ、BriskMap は BlueMap の 20〜34%。

**ブラウザで形を組み立てる方式でも、利用者の端末にかかる負荷は BlueMap より軽い。** 仮説では「組み立ての分だけ重くなる」と見ていたが、逆だった。

### 公平性についての注意（BriskMap に有利な差）

- BriskMap は色だけの単純な描画（テクスチャ・光・AO なし、シェーダーも簡単）。**1 周中の CPU の差の一部は、この描画の簡単さによる。** 読み込み時の差（転送量・GPU バッファ）は、データ形式の差がほとんど。
- 階段・草などをすべて立方体として描いている。実際の形にすると頂点は増える。
- BriskMap の JS ヒープは Worker を含まない（BlueMap もメインスレッドのみ）。
- 「落ち着いた」判定の 2 秒の待ち時間中も、BriskMap は毎フレーム描画し続けている（BlueMap は変化がないと描画しない）。この分は BriskMap に不利に働いている。

### 案 B（BlueMap 既定設定）について

- BlueMap の既定（近距離 100、遠景 2,000）では、転送量 27.8 MB・落ち着くまで約 2.65 秒・GPU テクスチャ 61〜95 MB。遠景（lowres）が転送量と GPU メモリの大半を占める。
- BriskMap には遠景がまだ無いため、直接の比較はしていない。

## 次の一手 / 未検証事項

- テクスチャ・光を付けた場合の BriskMap の負荷（描画の簡単さによる差を取り除く）
- 遠景（2D データを使った低解像度表示）を作り、案 B と同じ条件で比べる
- スマホでの測定
- 60Hz の上限を外した fps 測定（`--disable-gpu-vsync --disable-frame-rate-limit`）

## 追加実験: テクスチャ・光・AO を付けた BriskMap（計画、2026-09-29）

描画の簡単さによる差を取り除くため、BriskMap のビューアにテクスチャ（BlueMap と同じ 26.3 のクライアント jar から作る）・面ごとの明るさ・頂点 AO を付けて、案 A を測り直す。

- **H10（読み込み）:** テクスチャ付きでも、読み込み中の CPU 時間は BlueMap 以下、転送量は BlueMap の 1/3 以下を保つ。
- **H11（描画）:** カメラ 1 周中の CPU 時間は BlueMap の 60% 以下。
  - 棄却条件: 60% を超える。その場合、平らな色での 20〜34% は主に描画の簡単さによる差だったことになる。
- 注意: BriskMap は立方体でないブロック（草・花・階段など）を立方体として描くため、まだ BlueMap より簡単。光は面の向きによる明るさと AO だけで、空の光・ブロックの光は無い（Paper が標準形式で光を保存しないため）。

### 結論（追加実験）

- **H10（テクスチャ付きでも読み込み負荷は BlueMap 以下、転送量 1/3 以下）: 採択。** CPU 57〜71%、転送量 7.5%。
- **H11（1 周中の CPU 時間が BlueMap の 60% 以下）: 採択。** 38〜53%。
- 描画を揃えると差は縮んだ（1 周中の CPU は 20〜34% → 38〜53%）。**色のみの比較での差のうち、おおよそ半分は描画の簡単さによるものだった。**
- それでも残る差の内訳: GPU プロセスの CPU はほぼ同等（70〜96%）で、差は主に renderer（BlueMap は three.js のシーン処理でメインスレッドを使う。BriskMap はチャンクごとに描画命令を出すだけ）。
- 読み込みの遅れ（0.42 秒 → 約 1.0 秒）は、AO 計算で組み立て時間が約 2.5 倍になったことと、テクスチャの読み込みによる。

### 追加実験で分かった課題

- **AO で組み立てが重くなった。** Node・4,096 チャンクで WASM greedy が 1,857 ms → 4,560 ms。WASM の JS に対する優位も 3.4 倍 → 約 1.16 倍に縮んだ（原因は未調査。チャンクごとに 16×384×16 の格子を初期化している処理などが疑わしい）。
- **AO の値が違う面はまとめられないため、greedy の削減率が 46% → 28% に下がった。**
- 表示の不正確さ: 短い草などの十字形モデルを立方体として描いており、上面に色付けがかからず白っぽい点に見える（負荷の比較には影響しない）。
- まだ BriskMap のほうが簡単な点: 立方体でないブロックの形、空の光・ブロックの光（Paper が標準形式で保存しないため）、水の半透明。
